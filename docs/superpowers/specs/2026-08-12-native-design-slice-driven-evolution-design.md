# Native Design 产品切片演进与渐进清理方案

> 日期：2026-08-12
>
> 状态：已确认
>
> 产品主线：继续确认并补充新的 Phase A
>
> 清理策略：局部替代即局部清理；不可逆数据退役独立审批

## 1. 决策摘要

Multica 取消独立、一次性的 Open Design V1 破坏性移除 Phase B，不再把全仓库旧符号清零、跨层原子删除和 migration 877 作为当前产品阶段。

后续只沿 Native V2 产品能力推进。每个功能切片在证明完整替代关系后，必须删除该切片实际触达范围内已经失去活动用途的 V1/Worker 分支、fallback、旧配置和旧测试；不得为了全仓库清零扩大到未触达模块。

`open_design_run`、non-V2 package rows、历史 archive/evidence/Preview 对象和 schema constraint 等不可逆数据退役，不进入普通功能切片。只有全部活动代码自然退出对应数据后，才允许提出独立规格、独立审批和独立验证。

## 2. 为什么替代独立 Phase B

独立 Phase B 需要同时修改 daemon、handler、service、router、SQL/sqlc、前端、配置、对象存储和数据库迁移。这些层之间存在强编译和部署依赖，必须一次性闭合；任何中断都会产生无法编译、无法验证或不可部署的中间状态。

这种计划从历史实现反推删除范围，缺少天然的用户价值边界。每删除一个底层符号都会继续发现更多调用方，范围不可预测，验证成本随依赖树扩散。

Native V2 产品切片则拥有明确的入口、输入、产物、失败语义和验收证据。以产品切片作为工作单元，可以先证明新能力，再删除被该能力完整替代的局部旧路径，使每次变更可理解、可测试、可回滚。

## 3. 已确认的路线边界

1. `2026-08-12-native-design-phase-1-closure-and-legacy-removal-design.md` 中独立 Phase B 路线被本方案替代；其中已经取得的 Phase A 自动化证据仍然有效。
2. `2026-08-12-open-design-v1-destructive-removal.md` 不再执行，原 Task 3–12 不得作为后续实现清单继续推进。
3. 后续开发只沿 Native V2 产品功能主线组织。
4. 每个 Native V2 功能切片必须清理其实际触达范围内已被完整替代的旧路径。
5. 不为了 clean grep、目录清空或旧名称归零而扩大当前功能范围。
6. 一个旧模块只有在没有活动调用方后，才允许整体删除。
7. 数据库行、表、约束和对象存储历史数据的不可逆清理必须单独提出、审批和验证。
8. 隔离分支 `feature/fengchen-fixed-v2` 只保留为取消路线的 checkpoint，不合入 `feature/fengchen`，不作为后续实现基线，也不计入产品进度。
9. 新 Phase A 的目标、切片和验收由后续产品讨论补充；本方案不提前代填需求。

## 4. 功能切片清理门禁

每个 Native V2 功能切片只有同时满足以下条件，才允许删除对应旧残留。

### 4.1 替代关系明确

必须指出旧入口、分支或数据读取由哪个 Native V2 入口完整替代。不能因为文件名、包名或注释含 Open Design/V1 就判定可删除。

### 4.2 调用范围有界

开始实现前列出当前切片触达的 API、daemon、handler/service、数据、Web/Desktop 和测试范围。清理只能发生在这份范围内；新增范围必须重新评估，而不是沿依赖树无限扩张。

### 4.3 V2 正向证据先通过

必须先证明 Native V2 正常流程可用，再删除旧路径。测试应通过真实边界验证行为，不能只测试内部 helper。

### 4.4 失败和安全语义不退化

取消、失败、重试、坏包、越权、对象存储失败和 completion 重放必须继续保护 draft/saved。删除旧分支不得产生空成功、半完成内容、静默 fallback 或权限放宽。

### 4.5 活动消费方先迁移

Server、daemon、Web/Desktop 和 API schema 中属于当前切片的活动调用方必须先迁移到 V2。只要仍有活动调用方，就不能删除提供方。

### 4.6 建立局部负向合同

当前切片内的旧入口必须明确拒绝、不可达或不再注册。不得留下半活动 alias、双读、兼容转换或隐藏 fallback。

### 4.7 普通功能切片不退役历史数据

功能 PR 只允许停止新的旧链路读写并删除死代码，不删除历史行、对象或数据库表，也不收紧会拒绝现有历史数据的 schema constraint。

### 4.8 验证范围跟随改动

至少运行当前切片的 Go/TypeScript 定向测试、相关 package 回归、typecheck 和 GitNexus `detect_changes`。如果切片影响通用 Agent lifecycle，还必须证明非设计任务的 claim、execute、complete、fail、cancel 和恢复没有变化。

### 4.9 一个切片一个可回滚提交集

不能把多个独立旧模块堆进同一次删除。每个切片应能作为整体回滚，不依赖恢复另一套旧运行链路。

### 4.10 文档只记录事实

每个切片必须写明已清理的局部路径、仍然保留的旧模块、未处理的数据和实际验证结果。局部清理不得描述为 V1/Open Design 全面退役。

## 5. 新 Phase A 待确认结构

在后续产品讨论完成前，只保留以下结构，不填写未经确认的具体需求。

### 5.1 目标与用户价值

待确认这一阶段最终让用户获得什么能力，以及什么结果能证明该能力有实际价值。

### 5.2 真实使用闭环

待确认入口、用户选择的 Agent、仓库和参考输入、生成产物、在线 Preview/UI Kit、调整与保存流程。

### 5.3 验收证据

待确认真实 Agent、真实仓库 grounding、用户 Chrome 的视觉/Network/Console、数据库断言、失败隔离和人工质量判断。

### 5.4 功能切片顺序

根据后续确认的产品目标拆分。每个切片必须携带第 4 节的局部旧残留清理门禁。

### 5.5 明确非目标

每轮计划必须写明未进入当前切片的旧模块、数据迁移和后续设计能力，防止范围在实现中扩张。

### 5.6 最终数据退役候选

这里只允许记录观察项，例如 `open_design_run`、non-V2 package rows 和历史对象；不批准、不排期、不实施。
